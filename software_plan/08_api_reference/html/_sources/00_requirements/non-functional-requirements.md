# 非功能需求

| ID | 类别 | 需求与度量 |
|---|---|---|
| NFR-001 | 语言 | 所有自研运行时代码使用 Python；第三方容器内部语言除外。 |
| NFR-002 | 架构 | 采用端口/适配器分层；领域层不得依赖工作流引擎、Slurm 或容器 API。 |
| NFR-003 | 类型 | 公共 API、配置和工件使用明确类型；Pydantic 模型可导出 JSON Schema。 |
| NFR-004 | 可扩展 | 新 implementation 通过 entry point 安装，核心 recipe 不修改即可选择。 |
| NFR-005 | 可维护 | 单一模块具有一个主要科学职责；循环依赖为零；偏离必须记录 ADR。 |
| NFR-006 | 可测试 | 领域逻辑分支覆盖率目标 ≥90%；每个插件有 contract test，每个 adapter 有 collector fixture。 |
| NFR-007 | 可复现 | 生产容器锁定 OCI digest；参考、配置、参数和工件均有 checksum/hash。 |
| NFR-008 | 离线 | 正式运行阶段不得下载、安装、升级或 patch 工具；依赖在预备阶段完成。 |
| NFR-009 | 安全 | 外部命令使用 argv，禁止 `shell=True`；路径和 manifest 字段必须校验。 |
| NFR-010 | 可靠 | 任务状态持久化；失败可诊断；缓存损坏不得被误判为成功。 |
| NFR-011 | 恢复 | 已成功且 cache key 未变化的任务在 resume 时不得重复执行。 |
| NFR-012 | 隔离 | 一个 case 或可选支线失败不得无条件终止其他独立 case。 |
| NFR-013 | 性能 | 编排开销应远小于第三方工具运行时间；大型工件不在 Python 进程中整体载入。 |
| NFR-014 | 扩展 | 支持至少数百个 case 和数千个 shard 的 DAG，调度频率可受 site profile 限制。 |
| NFR-015 | 资源 | CPU、内存、时限、scratch、GPU 和 partition 可由实现默认值与 site override 合并。 |
| NFR-016 | 兼容 | 本地与 Slurm 对相同科学配置生成等价科学工件。 |
| NFR-017 | 可观察 | 每个 task 有结构化日志、时间、资源、尝试次数、容器和错误类别。 |
| NFR-018 | 审计 | 发布工件可追踪到原始输入和所有父工件；记录最终解析后的配置。 |
| NFR-019 | 科学连续性 | 旧/新比较基于规范 identity、字段和容差；语义差异须审批。 |
| NFR-020 | 数据完整性 | 关键工件写入采用临时路径加原子提交；伴随索引和 shard 集合必须完整。 |
| NFR-021 | 可移植 | 科学 recipe 不包含站点 partition、account 或绝对 scratch 路径。 |
| NFR-022 | 易用 | 配置错误在提交计算前汇总报告；CLI 同时支持人类和 JSON 输出。 |
| NFR-023 | 许可 | 插件 descriptor 声明许可证和凭据要求；无许可时 fail-fast 或明确跳过。 |
| NFR-024 | 供应链 | 镜像、模型、补丁和参考 bundle 有来源、版本、digest/checksum 与构建记录。 |
| NFR-025 | 文档 | 每个模块、接口和插件的需求、配置、测试及验收链路完整。 |
| NFR-026 | 质量 | format、lint、strict type-check、unit/contract tests 和文档链接检查全部通过后方可合并。 |

## 优先级

- **P0**：NFR-001～012、016～020、023～026，首期发布前必须满足。
- **P1**：NFR-013～015、021～022，架构验证阶段确定基线并在首期持续测量。

## 冲突处理

科学正确性高于运行吞吐；可复现性高于运行时自动安装的便利；显式失败高于静默 fallback；稳定领域契约高于对任一执行引擎的便利封装。冲突无法按这些原则解决时必须新增 ADR。
